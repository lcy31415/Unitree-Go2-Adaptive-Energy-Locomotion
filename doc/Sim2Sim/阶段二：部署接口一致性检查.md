

这一阶段的目标是：

> **确认 MuJoCo + `go2_ctrl` 在部署时构造出的策略输入、动作和底层控制参数，与 IsaacLab 训练阶段完全一致。**

Sim2Sim 最常见的问题并不是 ONNX 网络本身错误，而是：

```text
IsaacLab 训练时的 Policy Interface
                 ≠
MuJoCo 部署时的 Policy Interface
```

因此，本阶段本质上是在比较两端：

```text
训练侧
IsaacLab / unitree_rl_lab
        │
        │ 逐项对齐
        ▼
部署侧
go2_ctrl / unitree_mujoco
```

最重要的检查关系可以概括为：

|检查项|IsaacLab 训练侧来源|MuJoCo 部署侧来源|
|---|---|---|
|Observation|Task 的 Observation 配置|`deploy.yaml` + `unitree_articulation.h`|
|History|Observation `history_length`|`deploy.yaml` + Observation Manager|
|Joint Order|Go2 robot / joint 配置|`joint_ids_map` + `LowState`|
|Action|`JointPositionAction` 配置|`deploy.yaml` + Action Manager|
|Default Pose|Go2 `init_state`|`deploy.yaml`|
|PD Gain|Go2 actuator 配置|`deploy.yaml` + `State_RLBase.h`|
|Control Period|IsaacLab env/control 配置|`deploy.yaml::step_dt`|
|Policy Interface|Actor 网络配置|`policy.onnx` 输入/输出|

## 2.1 Observation 一致性

### IsaacLab 训练侧

策略训练时使用的单帧 Observation 为：

```text
base_ang_vel          3
projected_gravity     3
velocity_commands     3
joint_pos_rel        12
joint_vel_rel        12
last_action          12
───────────────────────
总计                 45
```

这些定义来自 IsaacLab 任务的 Observation 配置，并在策略导出时写入：

```text
<run>/params/deploy.yaml
```

例如当前 `deploy.yaml` 中记录：

```yaml
observations:
  base_ang_vel:
    scale: [0.2, 0.2, 0.2]
    history_length: 30

  projected_gravity:
    scale: [1.0, 1.0, 1.0]
    history_length: 30

  velocity_commands:
    scale: [1.0, 1.0, 1.0]
    history_length: 30

  joint_pos_rel:
    history_length: 30

  joint_vel_rel:
    scale: [0.05, ...]
    history_length: 30

  last_action:
    history_length: 30
```

因此：

```text
45 × 30 = 1350
```

这与导出的 ONNX：

```text
Input:
obs [1, 1350]
```

完全对应。

### MuJoCo 部署侧

MuJoCo 并不会直接产生这 1350 维 Observation。

它首先产生：

```text
IMU
joint q
joint dq
...
```

随后通过：

```text
MuJoCo
   ↓
LowState
   ↓
unitree_articulation.h
   ↓
Observation Construction
```

重新得到：

```text
base_ang_vel
projected_gravity
joint_pos
joint_vel
...
```

再由部署框架按照 `deploy.yaml` 进行 scale、relative operation、history stacking 等处理。

因此这里真正比较的是：

```text
IsaacLab训练：
Task Observation Config
        ↓
45维 observation

MuJoCo部署：
LowState
   ↓
Observation Construction
   ↓
45维 observation
```

两边不仅要求：

```text
维度一样
```

还必须保证：

```text
顺序
物理含义
单位
坐标系
scale
clip
history排列
```

全部一致。

例如训练时：

```text
joint_vel_rel × 0.05
```

那么部署时也必须：

```text
joint_vel_rel × 0.05
```

否则虽然仍然是 1350 维，Policy 看到的数据分布已经改变。

## 2.2 关节顺序一致性

关节顺序是 Sim2Sim 中非常容易被忽略的问题。

### IsaacLab 训练侧

Go2 的 SDK 关节名称定义来自：

```text
source/unitree_rl_lab/unitree_rl_lab/assets/robots/unitree.py
```

其中：

```python
joint_sdk_names=[
    "FR_hip_joint", "FR_thigh_joint", "FR_calf_joint",
    "FL_hip_joint", "FL_thigh_joint", "FL_calf_joint",
    "RR_hip_joint", "RR_thigh_joint", "RR_calf_joint",
    "RL_hip_joint", "RL_thigh_joint", "RL_calf_joint"
]
```

即 Unitree SDK 顺序：

```text
0   FR_hip
1   FR_thigh
2   FR_calf

3   FL_hip
4   FL_thigh
5   FL_calf

6   RR_hip
7   RR_thigh
8   RR_calf

9   RL_hip
10  RL_thigh
11  RL_calf
```

但是 IsaacLab 内部的 joint 顺序并不一定与 SDK 顺序相同。

### MuJoCo 部署侧

导出的：

```text
deploy.yaml
```

保存了：

```yaml
joint_ids_map:
[3, 0, 9, 6, 4, 1, 10, 7, 5, 2, 11, 8]
```

部署端读取状态时：

```cpp
data.joint_pos[i] =
    lowstate->msg_.motor_state()[data.joint_ids_map[i]].q();
```

发送动作时同样执行：

```cpp
motor_cmd()[joint_ids_map[i]].q() = action[i];
```

所以：

```text
Unitree SDK / MuJoCo顺序
          ↕
     joint_ids_map
          ↕
IsaacLab Policy内部顺序
```

由这一映射完成转换。

如果这里错误，即使 Policy 完全正常，也可能出现：

```text
Policy认为：
FL_hip 应该抬起

实际发送：
另一个关节发生运动
```

机器人通常会立即失稳。

## 2.3 Action 定义一致性

### IsaacLab 训练侧

训练时采用：

```text
JointPositionAction
```

Action 并不是直接作为绝对关节角，而是作为相对于默认姿态的偏移。

配置中：

```yaml
scale:
[0.25, ..., 0.25]

offset:
[0.1, -0.1, 0.1, -0.1,
 0.8, 0.8, 1.0, 1.0,
 -1.5, -1.5, -1.5, -1.5]
```

因此：

# [  
q_{\mathrm{des}}

q_{\mathrm{default}}+0.25a  
]

### MuJoCo 部署侧

ONNX 只输出：

```text
actions [1, 12]
```

这些 12 个数不能直接发送给电机。

部署端必须继续经过：

```text
policy.onnx
      ↓
12维 action
      ↓
Action Manager
      ↓
× action_scale = 0.25
      ↓
+ default_joint_pos
      ↓
q_des
```

所以这里检查的是：

```text
IsaacLab JointPositionAction
            =
部署端 JointPositionAction
```

其中：

```text
action_scale
default_joint_pos
action顺序
```

必须全部相同。

## 2.4 Default Joint Position 一致性

### IsaacLab 训练侧

Go2 默认姿态来自：

```text
UNITREE_GO2_CFG
```

例如：

```python
joint_pos={
    ".*R_hip_joint": -0.1,
    ".*L_hip_joint": 0.1,
    "F[L,R]_thigh_joint": 0.8,
    "R[L,R]_thigh_joint": 1.0,
    ".*_calf_joint": -1.5,
}
```

### 部署侧

对应参数被写入：

```yaml
default_joint_pos:
[0.1, -0.1, 0.1, -0.1,
 0.8, 0.8, 1.0, 1.0,
 -1.5, -1.5, -1.5, -1.5]
```

并同时作为：

```yaml
actions:
  JointPositionAction:
    offset: [...]
```

因此必须确认：

```text
训练 default pose
       =
部署 default pose
```

否则即使相同 Action，也会得到完全不同的 `q_des`。

## 2.5 PD 参数一致性

这是本项目实际发现的一个重要问题。

### IsaacLab 训练侧

Go2 actuator 参数来自：

```text
source/unitree_rl_lab/unitree_rl_lab/assets/robots/unitree.py
```

实际配置：

```python
UnitreeActuatorCfg_Go2HV(
    joint_names_expr=[".*"],
    stiffness=25.0,
    damping=0.5,
    friction=0.01,
)
```

即：

```text
Kp = 25.0
Kd = 0.5
```

### MuJoCo 部署侧

部署端的：

```text
State_RLBase.h
```

会直接执行：

```cpp
motor_cmd()[i].kp() =
    env->robot->data.joint_stiffness[i];

motor_cmd()[i].kd() =
    env->robot->data.joint_damping[i];
```

而这些数据来自：

```text
deploy.yaml
```

但自动导出的文件最初却是：

```yaml
stiffness: [0.0, ..., 0.0]
damping:   [0.0, ..., 0.0]
```

于是会导致：

```text
Policy产生 q_des
        ↓
Kp = 0
Kd = 0
        ↓
无法正常进行关节位置控制
```

因此我们根据训练侧真实 actuator 配置，将其修正为：

```yaml
stiffness:
[25.0, ..., 25.0]

damping:
[0.5, ..., 0.5]
```

最终实现：

```text
IsaacLab actuator
Kp=25 / Kd=0.5
        =
MuJoCo部署 LowCmd
Kp=25 / Kd=0.5
```

这是非常典型的 Sim2Sim 问题：

> **神经网络相同，并不意味着底层 actuator 行为自动相同。**

## 2.6 控制频率一致性

控制频率也属于 Policy Interface 的一部分。

### IsaacLab 训练侧

策略按照固定 control timestep 训练。

当前导出的部署参数为：

```yaml
step_dt: 0.02
```

即：

[  
f_{\mathrm{policy}}=\frac{1}{0.02}=50\text{ Hz}  
]

### 部署侧

`State_RLBase` 中 Policy thread 使用：

```cpp
const std::chrono::duration<double>
desiredDuration(env->step_dt);
```

因此每：

```text
0.02 s
```

执行一次：

```text
Observation
   ↓
policy.onnx
   ↓
Action
```

所以需要满足：

```text
IsaacLab Policy Frequency
          =
go2_ctrl Policy Frequency
```

如果训练是 50 Hz，而部署错误地变成 100 Hz 或 25 Hz，即使所有 Observation 和 Action 都完全正确，机器人动力学行为仍然可能显著变化。
